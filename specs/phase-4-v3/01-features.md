# Phase 4 (v3) — Feature Specs

**Only if the project is still alive and has had a real security review.** This phase is gated on the "stage open-source" plan (build to a stable core, threat-model it, get a free review via OTF Security Lab or OSTIF, then publish) landing first — not just on the earlier phases shipping.

## Local-LLM MCP gateway for scoped AI access

The only defensible shape for AI access to a user's health records, reached after a dedicated adversarial review: **local-model-only, read-only, no tools, per-person scopes, deterministic drug-interaction checking with the LLM only narrating results — never dosing or triage output.**

### Why this shape

Cloud LLM access was rejected outright — it collapses the entire zero-data-flow legal posture (the thing that keeps this project out of DPDP fiduciary status, GDPR controller status, and HIPAA scope) for one feature, with no consent flow that legitimately unlocks an exception. Medication lists are diagnoses in disguise (a specific antiretroviral regimen reveals HIV status even without a diagnosis field) — scopes bound what enters a query's context, they cannot bound what a model infers from it, so **per-person isolation is the only real technical control**, not category-based redaction. Live/standing access for any external party (including a doctor) was separately killed as the same unsolved group-key-management primitive as a rejected family peer-network feature — this gateway is local and single-user-facing, not a sharing mechanism.

### Confirmed against current (2026) MCP ecosystem research — this plan is still well-grounded

- **MCP is genuinely cross-industry now**, not an Anthropic-only bet — production-grade MCP support confirmed directly in OpenAI's Agents SDK and Microsoft's Semantic Kernel; governance sits under a Linux-Foundation-adjacent structure (Apache 2.0/CC-BY-4.0), not single-vendor control. The spec has evolved additively (no breaking rewrites) since its 2024 introduction. This is a durable bet for a multi-year nonprofit project.
- **No SMART-on-FHIR-equivalent scope taxonomy exists for MCP, and none is coming.** MCP's OAuth 2.1 authorization layer is real but explicitly designed for *remote* servers — for local/stdio deployments (this gateway's planned shape), the spec itself recommends environment-based trust plus client-side sandboxing instead of OAuth. A proposal that would have supplied fine-grained, SMART-like scopes (RFC 9396 Rich Authorization Requests) was opened and closed without shipping as of June 2026. **Build a custom per-person scope namespace** (e.g., `health:medications:read:person:<id>`) — this is necessary, not a stopgap for a standard that's coming.
- **Directly usable security guidance already exists.** MCP's official Security Best Practices documentation has a "Local MCP Server Compromise" section matching this gateway's exact deployment shape: use `stdio` transport restricted to the local client, or local HTTP behind an auth token/Unix domain socket; sandbox with minimal privileges; require explicit, non-truncated consent dialogs before executing a local server config. Also documents named attack classes worth designing against specifically: **Tool Poisoning** (hidden instructions in tool descriptions invisible to the user but visible to the model — directly relevant if any document text ever enters a tool's context), **MCP Rug Pulls** (a trusted server silently changing behavior post-approval — mitigate by version-pinning and checksum-verifying the server), **Tool Shadowing**, **Confused Deputy**, **Token Passthrough** (a server must never forward a token it received to a downstream API unvalidated), **Session Hijacking** (never use a session ID as authentication).
- **Open design question to resolve before this phase's build starts**: confirm the AI client is **in-app** — an embedded local LLM running in the same Flutter process — rather than an external client (e.g., the user's own separate Claude Desktop installation) reaching into the phone. A closely comparable real project, `xmartlabs/vytalLink` (Flutter, MIT, active — an embedded local MCP server over Apple Health/Google Health Connect data for AI assistants, a near-exact analog), started pure-local and **later added a cloud-hosted server option**, most likely because existing MCP clients (Claude Desktop, ChatGPT desktop) aren't built to discover or reach a server living only on a phone. If this project's client is in-process, that discovery problem never arises. If any future roadmap thread imagines a *separate* external AI client reaching into the device, the connectivity/discovery story needs to be designed explicitly, since MCP's own transports (stdio-subprocess, HTTP/SSE) don't have a mobile-first idiom yet.
- **Tooling exists in this project's chosen stack.** `dart_mcp` is an official package from the Flutter/Dart team (`labs.dart.dev`, still labeled "experimental"); `llama.cpp` and MLC-LLM both have current, maintained Flutter/Dart bindings for the local model itself. A small (1–3B parameter) quantized model for the narration-only role (summarizing pre-computed deterministic results, answering questions about the user's own already-fetched records) is confirmed realistic on mid-range Android hardware — an integration and quantization-tuning problem now, not a research-stage capability gap. Dated tooling note: Google's MediaPipe LLM Inference API is now maintenance-only; new on-device work should target LiteRT-LM instead.
- **This niche (personal health data via MCP) is real but early-stage.** Roughly 10 independent Apple Health MCP server projects exist on GitHub, all read/narrate-only (matching this project's philosophy exactly) — none implement multi-person scoped consent or deterministic interaction-checking. This project's planned design would be more rigorous than anything currently shipping in this space.

### Binding design constraints (unchanged from earlier planning, restated here since this is where they get built)

- Local-model-only, no cloud LLM path, ever, for this feature.
- Read-only, no tools — the model cannot write to the vault under any circumstance.
- Per-person, per-category, purpose-bound, time-bound scopes with a default expiry (no "forever" grant) and a subject-readable audit log of every query made against their data.
- Drug-interaction checking is a deterministic lookup against a real database; the LLM only narrates the result, never computes it.
- Hard output filters: no dosing numbers, no start/stop-medication directives, no triage dispositions ("you don't need the ER"). These are refusal categories enforced by a post-generation filter, not prompt-level instructions alone.
- Mental health, reproductive health, genetics, and deceased-relative entries are excluded from AI scope by default.

## SMART Health Links (KTC profile)

Only pursue if Indian institutional adoption of SMART Health Links materializes (the "Kill the Clipboard" initiative and its KTC profile are the reference architecture to track). Until then, F8/F13's simpler one-shot and pairwise mechanisms cover the actual need without depending on institutional uptake that may never arrive.

## ABDM import adapter

Design the domain model to already be profile-compatible (ABHA number as an optional `Patient` identifier, NRCES-profile-shaped resources) so this is an adapter when built, not a rewrite — but do not attempt actual ABDM HIU/Gateway registration and integration until there's real, demonstrated user demand. It's a large compliance lift (NHA sandbox onboarding, a real security/consent-artifact integration) that doesn't belong on the critical path for a solo developer.

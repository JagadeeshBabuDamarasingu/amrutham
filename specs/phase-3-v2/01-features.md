# Phase 3 (v2) — Feature Specs

Depends on infrastructure that doesn't exist yet (the QR/PAKE pairing primitive below) — sequence this strictly after phase 2, not in parallel with it.

## F13 — Pairwise time-boxed sharing

This is the resolved design for a "peer-to-peer" family-sharing request, reached after a dedicated adversarial review. It is not a new capability distinct from what was already scoped in earlier planning as "MedFriend-style missed-dose visibility, patient-controlled" — it's that same idea with the missing design detail filled in.

### Why this shape, and not the alternatives that were considered and rejected

Three readings of "sharing for a specific time, then automatically cuts" were tested:
- **A literal proximity-bound link** (Bluetooth/WiFi Direct/local network) — rejected. It only works while both devices are physically near each other, which doesn't fit the motivating scenario (a family member sees another's medication list for 48 hours while traveling — the two devices are never co-located for that window).
- **A real-time internet channel** — rejected. Even using an out-of-band channel (e.g., WhatsApp) to carry the initial WebRTC signaling handshake — a real, legitimate technique, since SDP offer/answer exchange only needs to happen once and doesn't strictly require a dedicated signaling server — this still needs a TURN relay for the actual data whenever STUN-based NAT traversal fails, which is common given India's prevalent mobile carrier-grade NAT. And a live session can't realistically survive 48 hours of app backgrounding, network changes (WiFi↔cellular), and OEM battery management regardless of how the connection started. Pursuing this reintroduces the exact always-on hosted-infrastructure liability that a peer-to-peer family circle feature was killed for earlier in planning — relocated from "web viewer" to "signaling/TURN relay," not eliminated.
- **A BitTorrent/swarm-style comparison was also explicitly considered and rejected**: P2P swarm networks are robust because no *specific* pairwise connection has to succeed (if peer A can't reach peer B, get the data from peer C instead). Family sharing is inherently a fixed, private, two-party problem — exactly one source, exactly one destination, no substitutable alternative — so the technique that makes BitTorrent resilient doesn't transfer.
- **Periodic auto-refreshing copies over existing rails** — the only option that survived. It requires no new hosted infrastructure, and honestly, it isn't "live" in any meaningful sense — it's the already-existing one-shot share mechanism (F8), delivered repeatedly.

### Design

- **Pairing**: an in-person QR/PAKE (password-authenticated key exchange) ceremony — never a forwardable link. (On WhatsApp specifically: forwarding is exactly why a link-based invite is unsafe — whoever taps a forwarded link *is* the intended recipient as far as the protocol can tell.)
- **Delivery is strictly read-only.** Never a live socket, never bidirectional, never reusing F7's sync conflict-resolution machinery (that exists for one person's *own* multi-device editing, not cross-person grants). Two delivery paths, chosen per scenario:
  - **Existing share-sheet rails** (WhatsApp/print/show-screen, same mechanism as F8), refreshed on a timer or on-demand. The honest floor: no new infrastructure at all, but each refresh needs the sender to act (tap share again) — neither WhatsApp nor any consumer messaging app exposes a silent/background-send API to third-party apps, and there's no legitimate way for the recipient's app to programmatically read an incoming message either (the only technical path to that, Android's Notification Listener API reading notification text, is a fragile, heavily-restricted anti-pattern this project avoids elsewhere).
  - **Provider-native sharing** (see below) for delivery that updates without the sender manually re-sharing each time.
- **Cloud provider mechanics** — researched specifically for this feature:
  - **Google Drive is primary.** Native expiration-date sharing is Workspace/Education/Nonprofit-edition-only, not available to personal Gmail accounts — so **expiry is self-built**: a scheduled job on the sharer's device calls Drive's `permissions.delete` after the bound set at pairing time. Share at the **file level only, never a folder** — picking a folder via Google's Picker API grants metadata access, not recursive read access to its contents (that needs the restricted `drive.readonly`/`drive` scope and Google's CASA verification process). Have the recipient select the shared file via the Picker's "Shared with me" view — this keeps the app on the non-sensitive `drive.file` scope, avoiding CASA entirely. Drive is the recommended default given India's Android/Google-account market dominance, despite needing self-built expiry.
  - **Microsoft OneDrive is the documented secondary option.** It's the only provider where native expiry-to-a-named-recipient actually works (`driveItem: invite`, taking both `recipients` and `expirationDateTime` in one call), with essentially zero app-verification burden for personal Microsoft accounts (no CASA-equivalent, no user cap — publisher verification is explicitly a work/school-tenant concept that doesn't apply here). Two catches: gated behind a **paid** Microsoft 365 Personal/Family subscription, not free OneDrive; and the natural "shared with me" discovery endpoint (`/me/drive/sharedWithMe`) is deprecated and dies entirely in November 2026 — implementation must resolve a specific known share ID via `/shares/{id}/driveItem` rather than enumerating (the app's own pairing exchange can carry the share ID directly, so this isn't a blocker, just a design constraint to build against).
  - **Dropbox is excluded from this feature.** It cannot do per-recipient-with-expiry sharing on any personal tier at all — its expiration feature is a *link* property (Business-tier only), never a property of the actual per-recipient sharing primitive. Its otherwise-lighter compliance burden (flat scope, no CASA-equivalent) is irrelevant given this structural gap.
- **Binding anti-coercion requirement**: a **persistent, hard-to-miss indicator on the data owner's own device for the entire sharing duration** — e.g., "Dad's meds are being shared with Sister until Thu 6pm — stop now." A multi-day auto-refreshing window otherwise inverts this project's established anti-coercion principle (expiry is supposed to work by forcing pressure to *repeat*, which makes coercion visible and costly) — without this indicator, one moment of coercion or unattended phone access buys a coercer an entire multi-day feed with zero further friction.
- **Binding honest language, no exceptions**: never "cuts access," "revokes," or "ends the connection." Anchor on delivery stopping, not access ending: *"[Recipient] will keep getting [Person]'s updated medication list until [date/time], then no more updates will be sent. Everything sent before then stays on their phone — this doesn't erase or recall anything they've already seen."*
